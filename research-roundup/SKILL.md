# 调研整理与分工文档（research-roundup）

把一堆资料——论文、代码仓库、数据集、网页、工具文档、别人（或 AI）写的调研报告、群消息——变成一份**队友拿到就能分头干活**的文档，并把里面的说法逐条核实。成品分三段：

1. **信息列表**：发生了什么，哪些说法站得住（核对表、技术结论表、资源表）。
2. **分工**：谁看什么、每项要回答什么问题、哪些事需要有人拍板（附推荐默认）、费力的任务写成指令卡。
3. **交接**：要登记进总表的行、未解决问题、证据放在哪里。

最前面是"先说结论"。多数读者只读这一块，所以它必须能单独转发，而且数字要和正文逐字一致。

这个格式来自一个多人科研项目里反复使用的调研文档：每轮新资料出现就写一份，下一轮接着上一轮留下的问题往下做。它解决三件事：资料越堆越多没人敢信；每个人各看各的、重复劳动；做完不知道交给谁、怎么交。

## 开始前：弄清五件事

用户已经说明的就不要再问；缺哪件问哪件。

1. 资料是什么、在哪：一份报告、一个链接清单、几个仓库、一批论文？
2. 谁读、几个人分工、谁拍板。
3. 截止时间（写绝对日期和时区），以及"这之后只记录、不再改动"的冻结点。
4. 边界：能不能下载、运行代码、登录；哪些内容敏感、不能外传。
5. 有没有上一轮同类文档：有就沿用它的编号和格式，并接着它的"未解决问题"。

## 工作流

**1. 取材，只读。** 把资料读全再动笔。仓库先看最新提交，再读 README、文档、配置、结果表，并固定到某个提交；要引用的文本文件存进证据目录，文件名写成 `来源_版本前缀_路径`（路径里的斜杠换成下划线）。网页存文本或快照并记取回时间，接口数据存原始响应。需要登录、下载大文件、运行代码才能看到的，不做，写进"没做到"。

**2. 拆陈述，逐条核对。** 输入是报告或消息时，把它拆成一条条"可核的陈述"（一个事实一条，别把三个事实打包），按原顺序编号，写成表：`# | 报告说法 | 核对结果 | 证据`。"核对结果"以判定词开头：**属实**／**大体属实，说法要补**（方向对，但数字、范围、公式或措辞要修正，并写出怎么修正）／**有误，需更正**／**无法核实**（没有可访问的原始证据）。报告里的建议、设计方案不是事实，标**（建议，不判定）**；你自己补充的口径提醒标**（补充，不判定）**。细则见 `references/verification.md`。

**3. 提炼技术结论。** 从原文里挑出对读者有用的结论，每条一行：`# | 结论 | 出处 | 证据强度 | 对我们`。证据强度只用固定的几种说法（见下），读者据此判断能信到什么程度。"对我们"写成可行动的一句：用、不用、先验证什么。

**4. 填资源表。** 仓库、页面、数据、评估方法各一张表，字段固定（`references/structure.md`）。跨轮次只记"本次变化"。数据和评估方法打 A–D 等级。

**5. 写"先说结论"。** 5–12 条，每条一个发现，加上为什么重要、指向正文哪一节。顺序：报告主干是否可信、要更正的几处 → 最重要的新信息 → 对我们的含义 → 要先弄清的风险或规则 → 看不到的 → 要你们定的事。**最后写它**，因为它必须和正文数字一致。

**6. 分工。** 先写原则（谁管哪一块、★精读／○只看结论／✕不用看）；再把需要有人拍板的事写成决定块，每块给"推荐默认"；再按"截止前能不能改变一个决定"排优先级；再给每个人列文件和"要回答："；费力的任务写成指令卡交给执行者（人或 agent），你不替他跑。细则见 `references/assignment-handoff.md`。

**7. 交接。** 沿用六项：资料结论、新增的数据行、新增的评估方法行、可直接利用清单、证据位置、未解决问题清单。再加一张"谁交给谁、交什么、放哪里、何时"的表，一份编号的未解决问题（写明谁来了结），和上一轮遗留问题的进展表。

**8. 自查，并登记。** 运行 `python scripts/check_doc.py 文档.md --root 证据目录`（表格列数、占位符、§引用、编号、行数与判定统计、证据路径），再过一遍 `assets/checklist.md`。项目里如果有索引或勘误表，只追加一行，不改前文。

## 证据强度的说法

| 说法 | 意思 |
|---|---|
| 官方数据 | 权威来源的接口、规则页、官方评分器或文档原文 |
| 可复算 | 本文用手头数据重算过（脚本和输出在证据目录） |
| 原文 | 读了文档或配置原文 |
| 原文（代码） | 读了源码，没有运行 |
| 作者本地 | 作者自己的本地实验；读了文字和代码，没有逐个复算 |
| 作者官方读数 | 作者记录的权威来源给出的读数（例如公开榜单上的分数） |
| 作者自述 | 作者对自己做法的说法，未核对 |
| 推断 | 我们的推理，不是原文 |

可以连用（"官方数据加可复算"）。凡写"本地"的数字，一律是作者或我们自己的本地结果，不是权威分。

## 硬规则（以及为什么）

1. **只读，先固定副本再引用。** 不运行别人的代码，不下载大数据和模型权重，不登录。资料会改、会删，固定副本才能让结论日后可复核；运行陌生代码有安全和资源风险。无许可证的仓库只读不复制。
2. **每个数字写口径；写"可复算"必须真重算过。** 比例、差值、计数、排名用脚本从原始文件算，脚本和输出放证据目录。两个看似矛盾的数，先对口径（阈值、去重规则、时间点）再下结论。调研里最常见的错误，是把不同口径的数并排比较。
3. **来源强度分层，不抬升。** "作者说""作者本地实验""权威数据""我们复算"是四种东西。作者本地的分数不写成权威分，"没发现问题"不写成"已验证"。读者会按文字的强度做决定。
4. **没有对照证据，不宣称提升或因果。** 没验证写"未验证"，推理标"推断"。
5. **名字相同不等于同一人、同一团队、同一东西。** 只靠名字对上的标"未确认"；涉及个人或团队身份的只记观察，不下认定。
6. **规则、许可、合规类问题：条款逐字放证据文件，正文转述，给分类框架，不替人下结论。** 默认给保守做法（先自查，再决定要不要问主办方），并写明"这不是法律意见"。这类判断错了代价大，而且往往不可逆。
7. **正文不贴长段原文。** 逐字摘录放证据文件，正文转述，必要时引一句短话并注明出处。
8. **费 token、磁盘、时间的任务，写成指令卡交给执行者。** 指令卡含输入、做什么、输出、不做什么、成本。
9. **更正追加，不改前文。** 编号一经发出就不重排。发现自己旧文有错，在勘误里追加一行（旧说法 → 更正后 → 依据），新文里指向它；自己的错误也要写出来，并说明影响。
10. **凭据与隐私。** 文档里不出现密码、token、私钥；内部路径、人名能否外传，交付前问一句。

## 语言与文风

- 用用户使用的语言写。中文版用上面的版式词；英文版对应为：先说结论 = Key findings，信息列表 = Information，分工 = Assignments，交接 = Handoff，属实 = Confirmed，大体属实，说法要补 = Mostly right (needs qualification)，有误 = Incorrect，无法核实 = Unverifiable，不判定 = Not judged，要回答 = To answer。
- 说人话，但保留算法细节和输入输出：一个方法要说清输入是什么、怎么得到结果、输出是什么。术语第一次出现给一句解释。
- 日期写绝对日期（"10/27"，注明时区），不写"昨天""刚才"。不用对话式措辞（"如前所述""我们来看看"）。
- 表格优先于长段落；编号全文通用，引用时写"§1.4 第 5 条"，避免和别的表里的第 5 条混。
- 数字带单位和口径；分数一律注明"官方"还是"本地"。

## 资料很少时用精简版

少于 5 项资料或只有一两个读者时，只保留：先说结论、核对表（或技术结论表）、资源表、分工（每人一小段，含"要回答："）、未解决问题。决定块和指令卡只在确有决定要拍板、确有费力任务时才写。

## 输出位置

写在项目的分析或笔记目录下，文件名 `NN_主题.md`，NN 取当天文件夹里下一个空号（写入前再查一次，别人可能同时在写）；证据放同级的 `证据_主题/`，按用途分子目录（`外部表/`、`网页/`、`结果/`、`脚本/`）。行尾与同目录其他文件保持一致。

## 交付前

- 运行 `scripts/check_doc.py`，把它报出的行数和判定统计与开头的计数行对一遍。
- 过 `assets/checklist.md`。
- 在回复里说清三件事：文档在哪、哪些没做到（没登录、没下载、没运行、没复算）、需要用户拍板的事是哪几件。
